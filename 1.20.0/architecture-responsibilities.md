# Who owns what

When something happens in the cluster, the question is which layer reacts: the Operator, Percona XtraDB Cluster ([Galera](https://docs.percona.com/percona-operator-for-xtradb-cluster/1.20.0/glossary.html#galera)), Kubernetes, or you. This page answers it at a glance. For the detail of what you do and what the Operator does in each area, and for what never to change by hand, see [Responsibilities by area](https://docs.percona.com/percona-operator-for-xtradb-cluster/1.20.0/operator-boundaries.html). For an overview of the layers, see [Design and architecture](https://docs.percona.com/percona-operator-for-xtradb-cluster/1.20.0/architecture.html#the-four-layers).

Two rules explain most of the behavior:

- **You change the cluster only through the [Custom Resource](https://docs.percona.com/percona-operator-for-xtradb-cluster/1.20.0/glossary.html#custom-resource) and the user Secrets.** The Operator turns them into Kubernetes objects, and reverts manual changes to the fields it manages.
- **Each layer keeps its own part alive.** Kubernetes keeps Pods running, Galera keeps the data consistent, and the Operator keeps the objects and the day-2 tasks matching the Custom Resource.

## Change the cluster through the Custom Resource

A [Custom Resource](https://kubernetes.io/docs/concepts/extend-kubernetes/api-extension/custom-resources/) (CR) is the Kubernetes object that describes the cluster you want. It is a blueprint that the Operator uses to deploy and manage your cluster.

**The Custom Resource is the source of truth. Change the cluster by editing the CR.**

The Operator compares the CR against what is running about every five seconds and corrects any difference it finds. A change you make directly to a [StatefulSet](https://docs.percona.com/percona-operator-for-xtradb-cluster/1.20.0/glossary.html#statefulset), a Service, a Pod, or a managed Secret is drift. The Operator overwrites it, usually within seconds. If a change survives, this means the Operator does not manage that field yet. This doesn’t mean the change was accepted.

- **Edits to the fields the Operator manages do not persist.** The Operator reverts them and doesn’t raise an event.
- **Edits outside the CR can still cause damage before they are reverted.**

## The Operator

The Operator reads the Custom Resource, compares it with what exists in Kubernetes about every five seconds, and creates, updates or deletes objects to close the gap. It also runs the day-2 tasks: ordered restarts ([Smart Update](https://docs.percona.com/percona-operator-for-xtradb-cluster/1.20.0/architecture-reconciliation.html#update-strategies)), password changes, certificates, storage resizing, backups, restores, point-in-time recovery, cross-site replication channels, and [recovery after a full cluster crash](https://docs.percona.com/percona-operator-for-xtradb-cluster/1.20.0/architecture-workflows.html#full-cluster-crash-recovery).

**The Operator does not:**

- Control Galera at runtime. It writes the Galera configuration, but [quorum](https://docs.percona.com/percona-operator-for-xtradb-cluster/1.20.0/glossary.html#quorum), [SST](https://docs.percona.com/percona-operator-for-xtradb-cluster/1.20.0/glossary.html#sst) and [IST](https://docs.percona.com/percona-operator-for-xtradb-cluster/1.20.0/glossary.html#ist), and [donor](https://docs.percona.com/percona-operator-for-xtradb-cluster/1.20.0/glossary.html#donor) selection are handled by Galera itself.
- Handle Kubernetes node failures. It does not force-delete Pods stuck on a failed node or react to node taints. Kubernetes recreates a Pod from an unreachable node elsewhere only after the Node object is removed or the stuck Pod is force-deleted.
- Validate MySQL options. The contents of `spec.pxc.configuration` go into a ConfigMap as is.
- Install or upgrade CRDs and RBAC.
- Drop database users that you remove from `spec.users`.
- Repair broken cross-site replication. It only logs that the replication channel is not running.
- Renew self-signed certificates it generated without cert-manager.
- Report most problems as Kubernetes events. It emits events only for full cluster crash recovery, CA certificate rotation, and volume resize. Everything else is in the Operator logs and the Custom Resource status.

For each area in detail, see [Responsibilities by area](https://docs.percona.com/percona-operator-for-xtradb-cluster/1.20.0/operator-boundaries.html). For the objects the Operator creates, see [Objects the Operator creates](https://docs.percona.com/percona-operator-for-xtradb-cluster/1.20.0/objects-created.html) and [Services and ports](https://docs.percona.com/percona-operator-for-xtradb-cluster/1.20.0/services.html).

## Percona XtraDB Cluster and Galera

**Galera does:**

- Replicate every transaction to all nodes and certify it, resolving write conflicts.
- Maintain quorum and decide which nodes form the [primary component](https://docs.percona.com/percona-operator-for-xtradb-cluster/1.20.0/glossary.html#primary-component) that serves queries.
- Slow down writes with flow control when a node falls behind.
- Bring a joining node up to date: with IST from another node’s write-set cache ([gcache](https://docs.percona.com/percona-operator-for-xtradb-cluster/1.20.0/glossary.html#gcache)) if possible, or with a full SST through Percona XtraBackup otherwise. Galera also chooses the donor node.

**What the Operator sets up for Galera:**

- The list of peers to connect to, from the cluster DNS.
- A preferred list of SST donors that excludes `cluster1-pxc-0` (the HAProxy writer) and the node with the highest number.
- `pc.weight=10`, unless you set it yourself.
- Encryption of replication traffic when internal TLS certificates exist.
- `innodb_buffer_pool_size` and `max_connections` calculated from the Pod resources, unless you set them yourself. This requires a memory limit (`pxc.resources.limits.memory`). See [Auto-tuning MySQL options](https://docs.percona.com/percona-operator-for-xtradb-cluster/1.20.0/options.html#auto-tuning-mysql-options).

**Health as the Pod probes see it:**

- A database Pod is *ready* only when its node belongs to the primary component and is `Synced`. A node that is a donor counts as ready by default. Set the `AVAILABLE_WHEN_DONOR` environment variable of the `pxc` container to a value other than `1` to make a donor not ready. HAProxy’s own health check has a separate switch, `OK_IF_DONOR`, which is off by default. See [In-cluster failover](https://docs.percona.com/percona-operator-for-xtradb-cluster/1.20.0/failover-in-cluster.html#traffic-rerouting).
- The liveness probe tolerates long startups, SST and recovery, so a node that is busy catching up is not killed. A node that stays outside the primary component for about 30 seconds is restarted.
- See [Health checks and probes](https://docs.percona.com/percona-operator-for-xtradb-cluster/1.20.0/architecture-probes.html) for what the probes check and who acts on their result.

**What this means in practice:**

- A Pod that is `Running` but not `Ready` usually means Galera hasn’t finished bringing the node in: the node is still receiving an SST or IST, or it cannot reach the other nodes.
- An SST that keeps failing stops after `pxc.sstRetryCount` attempts, and the Pod stays not ready until you intervene. See [Limit SST retries](https://docs.percona.com/percona-operator-for-xtradb-cluster/1.20.0/sst-retry-limit.html).
- A bad option in `spec.pxc.configuration` shows up as `mysqld` failing to start, in the `pxc` container logs.

## Kubernetes

**Kubernetes does:**

- **Schedule Pods.** The Operator only writes the affinity rules, node selectors, tolerations, priority class and topology spread constraints you specify. The default anti-affinity is *required* on `kubernetes.io/hostname`: three database Pods need three schedulable nodes. Otherwise a Pod stays `Pending`, and after about a minute the Custom Resource status shows the scheduler’s message.
- **Provide storage.** The CSI driver and StorageClass provision volumes, bind them to zones, and expand file systems. A ReadWriteOnce volume ties the Pod to the node or zone where the volume can attach.
- **Run the network and DNS.** The database nodes find each other, and the proxies find the database nodes, by looking up the [headless Services](https://docs.percona.com/percona-operator-for-xtradb-cluster/1.20.0/glossary.html#headless-service) in cluster DNS. If DNS is broken, nodes cannot form or join the cluster, proxies lose their backends, and crash detection stops working.
- **Provision load balancers.** For `LoadBalancer` Services, the cloud provider creates the load balancer. Firewalls and source ranges are yours and the provider’s to manage.
- **Manage the Pod lifecycle.** Run probes, restart failed containers, enforce [PodDisruptionBudgets](https://docs.percona.com/percona-operator-for-xtradb-cluster/1.20.0/glossary.html#pdb) during node drains, and retry failed Jobs.
- **Collect garbage.** Delete objects owned by the Custom Resource when you delete it.

**Kubernetes does not:**

- Know anything about Galera beyond the [probes](https://docs.percona.com/percona-operator-for-xtradb-cluster/1.20.0/architecture-probes.html). A native StatefulSet rolling update waits for each Pod to become ready, but it doesn’t pause for a running backup, doesn’t wait for ProxySQL to bring the node back online, and doesn’t stop early when a Pod can’t start.
- Expand a volume whose StorageClass doesn’t allow it, or beyond your storage quota.

## You, the user

The Operator keeps the cluster matching the Custom Resource. Everything it cannot create or decide for you stays with you:

- Install and upgrade the CRDs and RBAC, which the Operator never applies. See [Upgrade CRD and the Operator](https://docs.percona.com/percona-operator-for-xtradb-cluster/1.20.0/update-operator.html).
- Provide capacity: enough schedulable nodes for the anti-affinity rules, and a StorageClass that allows volume expansion. See [Cluster lifecycle](https://docs.percona.com/percona-operator-for-xtradb-cluster/1.20.0/operator-boundaries.html#cluster-lifecycle) and [Storage](https://docs.percona.com/percona-operator-for-xtradb-cluster/1.20.0/operator-boundaries.html#storage).
- Provide credentials: the passwords in the user Secret, the backup storage credentials, and the PMM token. See [Users and Secrets](https://docs.percona.com/percona-operator-for-xtradb-cluster/1.20.0/operator-boundaries.html#users-and-secrets).
- Renew certificates when cert-manager isn’t installed, or when you supplied them. See [Manage certificates](https://docs.percona.com/percona-operator-for-xtradb-cluster/1.20.0/operator-boundaries.html#manage-certificates).
- Verify that backups restore, set retention, and keep copies outside the cluster storage. See [Back up the database](https://docs.percona.com/percona-operator-for-xtradb-cluster/1.20.0/operator-boundaries.html#back-up-the-database).
- Monitor cross-site replication, and repair it when it breaks. See [Cross-site replication](https://docs.percona.com/percona-operator-for-xtradb-cluster/1.20.0/operator-boundaries.html#cross-site-replication).
- Decide when to pause, upgrade, and restore. See [Database upgrades](https://docs.percona.com/percona-operator-for-xtradb-cluster/1.20.0/operator-boundaries.html#database-upgrades) and [Restore and point-in-time recovery](https://docs.percona.com/percona-operator-for-xtradb-cluster/1.20.0/operator-boundaries.html#restore-and-point-in-time-recovery).

## Unsafe configurations

The Operator refuses configurations that put availability or data at risk, such as fewer than three database nodes or running without TLS. See [Stay inside safe operating limits](https://docs.percona.com/percona-operator-for-xtradb-cluster/1.20.0/operator-boundaries.html#stay-inside-safe-operating-limits). To use one anyway, you opt in with a flag in the `spec.unsafeFlags` subsection. See [Override a safety check](https://docs.percona.com/percona-operator-for-xtradb-cluster/1.20.0/operator-boundaries.html#override-a-safety-check).

## How to tell which layer it is

Check these sources in order. Each one narrows down the layer.

1. **Custom Resource status and conditions.** `kubectl get pxc cluster1 -o yaml` shows the cluster state, the reconcile error message if any, and scheduling problems. An `error` state with a spec message points to the user. See [Status](https://docs.percona.com/percona-operator-for-xtradb-cluster/1.20.0/architecture-reconciliation.html#status).
1. **Events.** `kubectl get events --sort-by=.lastTimestamp` shows Kubernetes problems: scheduling, volume attachment and resize, image pulls, probe failures. The Operator itself adds events only for full cluster crash recovery, CA rotation and volume resize. See [Check the events](https://docs.percona.com/percona-operator-for-xtradb-cluster/1.20.0/debug-events.html).
1. **Operator logs.** `kubectl logs deployment/percona-xtradb-cluster-operator` shows what the Operator is doing or waiting for: a stuck rolling restart, a skipped backup, broken replication. Most Operator problems appear only here.
1. **Pod and container logs.** `kubectl logs cluster1-pxc-0 -c pxc` shows Galera and MySQL problems: SST failures, quorum loss, `mysqld` start failures. For backup and restore problems, read the logs of the Job. See [Check the logs](https://docs.percona.com/percona-operator-for-xtradb-cluster/1.20.0/debug-logs.html).
